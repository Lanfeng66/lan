# 微服务架构设计指南

## 第一部分：架构原则

### 1.1 微服务拆分的六个原则

**1. 单一职责（Single Responsibility）**
一个服务只做一件事。比如"用户服务"只负责用户注册、登录、认证；"订单服务"只负责订单创建、状态流转。

**2. 围绕业务能力组织（Business Capability）**
不要按照技术层（Controller-Service-DAO）拆分，而是按业务域拆分。订单相关的所有逻辑（包括它的 Controller、Service、DAO）都在同一个服务内。

**3. 去中心化数据管理（Decentralized Data）**
每个服务有自己的数据库，服务间不允许直接访问对方的数据库。这是最重要的原则，也是最容易被忽视的。

**4. 容错设计（Design for Failure）**
下游服务可能随时不可用。每个服务调用都需要有超时、重试、熔断、降级策略。

**5. 可观测性（Observability）**
每个服务必须有统一的日志格式、指标暴露、链路追踪注入。

**6. 独立部署（Independent Deployability）**
修改一个服务的代码，不需要重新部署其他服务。

### 1.2 微服务拆分的前置条件

不要为了微服务而微服务。满足以下条件再考虑拆分：

- 单体应用的工程团队超过 20 人，代码冲突成为瓶颈
- 不同模块的变更节奏完全不同（如订单每周改 3 次，支付每月改 1 次）
- 不同模块的扩容需求差异巨大（订单需要 50 个实例，管理后台只需要 2 个）
- 团队已经有了成熟的 CI/CD 和容器化基础设施

### 1.3 错误拆分模式

| 错误模式 | 问题 | 正确做法 |
|----------|------|----------|
| 按请求路径拆分（/api/user → 用户服务, /api/order → 订单服务）| 会导致跨服务事务 | 按聚合根边界拆分，DDD 限界上下文 |
| 过度拆分（每个表一个服务）| 网络开销爆炸，调试困难 | 从粗粒度开始，逐步细化 |
| 共享数据库 | 服务间紧耦合，改表结构要协调多个团队 | 每个服务独立数据库，通过 API 通信 |

## 第二部分：服务间通信

### 2.1 通信模式对比

| 模式 | 协议 | 适用场景 | 优缺点 |
|------|------|----------|--------|
| 同步 HTTP/REST | HTTP/1.1 | 查询类接口 | 简单直观，但不适合长调用链 |
| 同步 gRPC | HTTP/2 + Protobuf | 服务间高频调用 | 性能好，强类型，多语言支持 |
| 异步消息 | Kafka / RabbitMQ | 事件驱动、最终一致性 | 解耦，削峰，但增加复杂度 |
| 异步 Request/Reply | NATS / RSocket | 需要异步但要有返回值的场景 | 兼顾异步解耦和请求-响应模型 |

### 2.2 gRPC 服务定义示例

```protobuf
syntax = "proto3";

package docmind.search;

service SearchService {
  rpc Search(SearchRequest) returns (SearchResponse);
  rpc IndexDocument(IndexRequest) returns (IndexResponse);
  rpc DeleteDocument(DeleteRequest) returns (DeleteResponse);
}

message SearchRequest {
  string query = 1;
  int32 top_k = 2;
  repeated string filter_tags = 3;
  float min_score = 4;
}

message SearchResponse {
  repeated SearchResult results = 1;
  int64 total_count = 2;
  float elapsed_ms = 3;
}
```

## 第三部分：分布式事务

### 3.1 Saga 模式

当一次业务操作需要跨多个服务修改数据时使用 Saga。

**编排式 Saga（Orchestration）**：
由一个协调器服务按顺序调用各个参与服务，每一步成功则继续，失败则执行补偿操作。

```
创建订单 → 扣减库存 → 扣款 → 更新订单状态
   ↓ 失败     ↓ 失败      ↓ 失败
 无需补偿   恢复库存    退款
```

**编排式 Saga 实现示例（Python）**：
```python
class CreateOrderSaga:
    async def execute(self, order_data):
        try:
            order = await self.order_service.create(order_data)
            await self.inventory_service.reserve(order.items)
            payment = await self.payment_service.charge(order.total)
            await self.order_service.confirm(order.id)
        except InventoryError:
            await self.order_service.cancel(order.id)  # 补偿
            raise
        except PaymentError:
            await self.inventory_service.release(order.items)  # 补偿
            await self.order_service.cancel(order.id)   # 补偿
            raise
```

**协同式 Saga（Choreography）**：
各服务订阅事件，根据事件自行决定做什么。如"订单已创建"事件 → 库存服务自己减库存。

### 3.2 最终一致性

在微服务架构中，强一致性代价太高（需要分布式锁、两阶段提交）。多数场景接受最终一致性：

- 订单创建后，库存可能在 500ms 后才真正扣减
- 用户修改头像后，其他服务在 1 分钟内可能还是旧头像
- 使用事件溯源（Event Sourcing）保证所有变更可回溯

## 第四部分：API 网关

### 4.1 网关职责

- **路由转发**：根据路径将请求转发到不同服务
- **认证鉴权**：统一 JWT 验证
- **限流**：基于用户/API Key/IP 的限流
- **请求聚合**：一个前端请求可能需要调用多个后端服务，网关负责聚合
- **协议转换**：对外 REST，对内 gRPC

### 4.2 Kong 网关配置示例

```yaml
# 使用 Kong 的 declarative config
services:
  - name: search-service
    url: http://search-service.docmind.svc:8080
    routes:
      - name: search-route
        paths: ['/api/search']
        methods: ['GET', 'POST']
    plugins:
      - name: rate-limiting
        config:
          minute: 100
      - name: jwt
```

## 第五部分：可观测性

### 5.1 三大支柱

**日志（Logging）**：
- 结构化 JSON 日志
- 每条日志带 trace_id
- ELK 或 Loki 集中存储

**指标（Metrics）**：
- RED 方法论：Rate（请求速率）、Errors（错误率）、Duration（延迟）
- Prometheus + Grafana

**链路追踪（Tracing）**：
- OpenTelemetry 标准
- Jaeger / Grafana Tempo 后端
- 每个服务调用自动传播 trace context
